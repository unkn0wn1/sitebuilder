# 0009: SQLite with Drizzle, and a job table instead of a queue service

- **Status:** Accepted
- **Date:** 2026-11-17

## Context

Whether to support SQLite and Postgres from day one was open. Image processing, publishing, checks, scheduled publishing, email and backups all need work done outside a web request, and nothing in the architecture did that.

## Decision

- **SQLite only in v1**, through **Drizzle ORM** with `better-sqlite3`, in WAL mode. The schema is written to be portable (text ids, ISO 8601 text timestamps, JSON stored as text, no SQLite-only features), so a Postgres schema can be added later without changing services.
- **Migrations** are generated by `drizzle-kit` into `server/db/migrations/` and applied automatically on start-up.
- **Jobs live in a `jobs` table** in the same database. One worker loop runs inside the builder process: it claims the oldest due job with an atomic update, runs it, and records the result. Retries with backoff, a maximum attempt count and a visible error. No Redis, no separate queue service.
- Job kinds in v1: `publish`, `render_preview`, `media_renditions`, `run_checks`, `send_email`, `backup`, `purge_cache`, `bin_cleanup`. Publishing and checks run with a concurrency of 1, so the server is never swamped.
- Scheduled work (scheduled publish, nightly backup, bin clean-up) is simply a job with a `run_at` in the future.

## Consequences

- No extra services to install or back up. A backup of the database includes the job history.
- One process means a crash stops the worker too. Docker restarts it, and jobs that were running are retried after a lease timeout.
- Postgres is a later, contained change.
